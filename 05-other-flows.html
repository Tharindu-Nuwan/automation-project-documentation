Prepare for the flow you are checking

A flow is a sequence of actions, such as sign in, create a QR, edit it, or download it. Start from the same account condition and page as the test case. In this guide, an assertion is the result the automation checks; for a manual check, compare that expected result with what you see.

When a case needs an expired account, old QR records, simulated payment dates, or a deliberately failing server response, ask the automation maintainer to prepare that condition. Those conditions may be created by code rather than by normal form entry.

The sections below retain exact test labels and optional implementation details. You do not need to run API or database commands to use the preparation table.

Homepage and static previews

Homepage tests exercise navigation and QR type entry. Fit Your Needs has design, responsive and localization suites backed by fit-your-needs-preview.data.ts and translations; its factory is OQG-only. Static preview suites inspect homepage/Step 1/network preload behavior and product/locale-specific expected strings. Preloaded sample content is not user-created QR content. Its expected text comes from the static-preview datasets, not Step 2 defaults.

References: homepage specs, static preview specs, MainPage, FitYourNeedsPage.

Dashboard, My QR Codes and folders

Most ordinary dashboard cases register a fresh user, navigate to /qr-codes, perform navigation/account-state checks, then delete the user. Some change subscription expiry using UserApi.updateSubscriptionDate() to create an expired state without waiting days.

Folder tests cover create, rename, delete, duplicate, pause/activate, moving QRs, bulk actions, counts, empty/failure paths, cross-session behavior and responsive/cross-browser cases. Data is in folder-file-counter.data.ts and oqg3-2211.data.ts; shared flows are in folder-file-counter.helper.ts, create-from-folder.helper.ts, and oqg3-2211.helper.ts.

finishLoggedInCreate() combines Next/Create and waits for creation completion. Helpers create Website QRs at root or in a selected folder. Use returned QR/folder names to make assertions; .first() tests operate on the first visible record and need isolated data. A mocked delete failure is a controlled network failure, not proof the backend naturally returns that error. The reference exposes page.route() calls for these cases.

References: dashboard, My QR Codes, MyQrCodesPage.

Edit and persistence

The QR-details folder has per-type edit suites (Website, PDF, Links, vCard, Business, Images, Video, Apps, Coupon, MP3, Digital Menu, Facebook, Social Media and Event paths), plus download tests. Typical setup is fresh user → create/save QR → open edit → alter content → save → assert result. Actual cases may stop earlier or inspect only preview; use their assertions to state coverage precisely.

Do not reuse a setter blindly: creation helpers can append. QR name is the dashboard identifier; content headings are separate fields. Event's helper restores dates on reopening as a workaround, so use the dedicated persistence defect case when checking that issue. QR detail specs.

Downloads

Download tests select formats/sizes from dedicated data/constants, trigger a browser download, save/read artifacts where the test does so, and assert the relevant filename, extension, size, dimensions or behavior. A modal being visible is weaker evidence than a real file download. A non-empty .xlsx is weaker evidence than validating every exported analytics row.

Unique download page tests have a distinct route and setup. Some download matrices create QR types through shared recipes first, including protected scan content. Check account plan state: a free, trial, paid or cancelled user can see different download gates/banners. Exact paths and assertions: QR-details reference, download data.

My Account

General information covers profile values, email, phone, language, password and account actions; Billing Information covers personal/company form behavior and associated fields. Most inputs are generated in the spec or passed to AccountPage setters. Profile name, QR contact name, payment billing name and admin user name are distinct fields.

Email-change flows can require cleanup against a new email. Account deletion can make a subsequent teardown request redundant. Password cases should preserve the new value when testing login afterwards. Account specs, AccountPage.

In plain language: transactional emails are messages sent because of an account action, such as registration, verification or a password change. They are different from choosing the Email QR type in the creation form.

Transactional email

The four email spec files cover default emails, user-triggered events, password-changed behavior and delivery-related scenarios. They create the relevant user/subscription/QR state, record a timestamp, trigger the action, poll the mail catcher for recipient/subject, then inspect HTML/text/raw message and links/content as specified. Some conditions are negative: no email should arrive within the observation window.

Mailpit is the current client. Mailtrap.ts is only a compatibility re-export, and generated @mailtrap.com addresses do not require a real cloud mailbox. The application must be configured to deliver outbound test mail to the same catcher. EmailBodyPage is factory-backed for OQG/QCI; QR Email templates use a different page/helper system.

Sources: email specs, Mailpit, email constants.

Analytics

The analytics spec uses credentials declared inside the file and expected city/country sets. It relies on a populated account rather than seeding all history through the common register fixture. It tests date ranges, filters and export behavior; date boundaries use the run's current date. To reproduce manually, obtain authorized access to the designated analytics fixture account/data; an empty newly created account cannot satisfy these expectations. Analytics reference.

Prepared examples and optional setup tools

tests/tools contains generators, not ordinary pass/fail acceptance coverage. Generic Event/folder generators share a stored account through a lock and retain records for manual exploration. Event field-validation seeding has additional account-choice, run-ID and seed controls, and writes a manifest through its helper. Read tools reference before running. Use a specific tool path with the intended legacy project and controls; never include the folder in a broad onboarding smoke run.

The Event field seeder requires EVENT_VALIDATION_SEED=true and a nonempty EVENT_VALIDATION_RUN_ID (1–80 letters, digits, dots, underscores or hyphens). EVENT_VALIDATION_ACCOUNT selects local (default, LOCAL_USER_*), default (DEFAULT_USER_*), or dedicated (register once and retain .auth/event-validation-owner.json). It does not silently substitute a disposable user for a missing existing account. Its source guard accepts private/local hosts or the explicitly named oqg.devii.test-qr.com host; this is a code restriction, not a statement that that deployment is currently available.

Optional comma-separated EVENT_VALIDATION_FIELDS and EVENT_VALIDATION_CASE_IDS limit the selected scenarios. JSON/CSV manifests go to test-results/event-field-validation/<run-id>/<field>.*, with resumable checkpoints under .auth/event-field-validation/<run-id>/. Records include raw/display-safe input, expected and observed result, validation message, retained QR name/UID/folder, and outcomes such as accepted, rejected, sanitized, expectation mismatch, unsafe execution or operational error. This is the most direct handoff artifact when QAs need persistent examples to inspect manually. See manifest helper.
