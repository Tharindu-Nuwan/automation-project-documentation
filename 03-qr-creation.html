QR creation: types, fields, data, and completion

Start · Previous · Next: data cookbook

Create a QR in plain language

The creation form has three stages: choose the QR type, enter its content, then choose the QR design. The final Create action completes the flow. The pages after Create depend on whether you started as a signed-in user or a guest.

  1. Use the account and starting page named by the test case. A guest flow can ask for an email or a plan after Create; a signed-in flow can return to My QR Codes.
  2. In Step 1, select the type. If you choose Menu, also select Digital, PDF, or Website.
  3. In Step 2, enter the case's content. Use the type table below to identify fields and the input guide to find sample values and files.
  4. Record the internal QR name so you can find the result in My QR Codes. This name may differ from a title shown on the QR's public page.
  5. Check the preview where the case requires it. On a small screen you may need to open the preview first. Continue with Next when the required fields are complete.
  6. In Step 3, select the design options required by the case and click Create if the case includes saving.
  7. Check the exact expected result: a saved QR, a download, a guest signup page, or another specified outcome. If the case checks saved content, reopen that QR and compare the values. If it checks scanning, open its scan destination as a separate check.

Preview, saving, and scanning are different checks. Seeing the correct preview does not establish that the same content was saved or appears after scanning.

How to use the type and field tables

A recipe below means a reusable sequence that the automation follows to fill a QR form. You can use the field descriptions for manual entry. The code names are included so an automation maintainer can locate the exact implementation.

Default means the sample value used when a particular test does not supply another value. Generated means the automation makes a new value each time. To repeat a failed run, use its recorded value. For a new manual check, choose a suitable value only when the case allows that choice, and record it. File names refer to test upload files that your team must supply separately from this HTML guide.

Exactly how many types are implemented in this code?

The shared Step 1 selectors name 18 top-level types: Website, PDF, Links, vCard, Business, Images, Video, Apps, Coupon, MP3, Menu, WiFi, Facebook, Instagram, Social Media, WhatsApp, Event, and Email. Menu opens Digital, PDF, and Website choices. Counting those separately gives 20 selectable type/variant paths. This is a source inventory, not a claim that all 20 are deployed on every product.

QrCreationPage has 19 named full-content recipes for those paths except Email. Email uses dedicated Step 2 and EmailTemplatesPage helpers instead. Quick Website/DPF methods are additional shortcuts, not additional QR types.

There is no universal master matrix. tests/data/constants/global-constants.ts exports only 15 active qrTypes rows: it excludes Website and Email, leaves WiFi commented out, and includes only Digital Menu. Other matrices select their own types. A test that loops over that array covers only its selected types.

Sources: Step1 selectors, Step1 actions, creation recipes, global matrix.

Most ...QrCreate() recipes stop after filling Step 2 and return the internal QR name. They do not call Next/Create. The caller normally follows with clickStep2NextButton() and clickStep3CreateButton(). quickWebsiteCreate() performs both clicks but returns no name. website-qr.spec.ts has tests that only reach Step 3; those are content/navigation tests, not proof a QR was published or scanned.

Step 1 helper behavior is affected by onboarding; some paths need a repeated click to open Step 2. Help dialogs can reappear and intercept clicks. clickStep2NextButton() waits for its footer, normally waits for enabled state, pauses briefly, dismisses help, then clicks. For negative tests it supports { waitForEnabled: false }. clickStep3CreateButton() handles Step 3 help and readiness. When maintaining automation, preserve these readiness checks instead of replacing them with arbitrary delays.

Input-source legend

  • D — Default: fixed sample value used by the automation when the particular test does not provide its own value.
  • G — Generated: new sample text produced by Faker, a test-data generator; it can change between runs.
  • F — File: a particular upload sample stored with the test project.
  • S — Scenario: the particular test case or its data file supplies the value; use it instead of a default.
  • U — On-screen result: a value read from the running application, such as the QR name or its unique identifier (UID).

Most setters use pressSequentially(), which types rather than replaces. Some call clear() first; others do not. Reusing a creation setter on an already-filled edit field may append text. setEventTitle() and Email business name clear explicitly; read the helper before reusing it.

Many setters contain their own preview assertions. If a call that “just fills” times out, it may be waiting for the iframe text, not failing to enter data. Mobile preview can be hidden or zero-sized until opened; use the feature's mobile helper rather than assuming desktop visibility.

For manual Event checks: provide an Event title and both a start date and an end date. Check the All day choice and any time values required by the case. Use the calendar controls. The automation normally chooses tomorrow using the date of the machine running it.

Event: three distinct setup paths

  1. Guest content: openEventStep2() opens /create?step=1, selects Event, dismisses help and waits for footer readiness. It does not create an authenticated dashboard owner.
  2. Existing local account: loginLocalUser() reads LOCAL_USER_*. The helper comments describe a local stack where /register redirects; this is deployment context, not a universal rule.
  3. Fresh registered publishing: loginCreateAndPublishEventQr() registers through authorizeUser() unless an already authenticated user's object is passed. It goes to dashboard, selects Event, fills required content, names the QR, advances and creates. Returns { title, qrName, user }.

The minimal fillEventRequiredFields() sets title plus both start and end date, normally tomorrow, then sets the All day state through its toggle helper. Omitting end date can prevent progression. Date defaults use the execution machine's clock/local date formatting; a near-midnight CI run can differ from your laptop.

The fuller recipe's setEventTimes(startTime, endTime) is not a general-purpose arbitrary time setter: current implementation confirms the start picker default, and when arguments differ selects PM and 5 for end. For precise multi-row time scenarios inspect setEventRowHour() and the Event date specs. Passing two time strings does not guarantee that this helper selects those exact times.

loginCreateAndEditEventQr() calls restoreEventDatesInEdit(). That re-enters dates because the source documents lost Event date/time values on reopening (OQG3-2533). A passing later assertion does not prove original dates persisted. Event helper source explains this workaround.

openEventScanPage() reads QR link/UID, opens a new tab and only fills the scanner password if a gate is visible. With no gate, unconditional ScannedPage.authorize() would wait on a nonexistent field. Dashboard operations should use QR name; scanner content assertions should use Event title.

For manual Email QR checks: enter the Basic Information name and the first template's title and recipient email before checking other fields. Optional description, image, subject, body and icon depend on the case. This creates email-related QR content; account verification and password-reset messages are described under transactional email.

Email: content QR, not the transactional email system

openEmailQrStep2() enters /qr?step=1, selects Email, dismisses help/backdrop and waits for Basic Information. Name/business name is required; description and image have dedicated helpers. Supply first template title and recipient to avoid unrelated validation failures when testing Basic Information.

openEmailTemplatesEditor() skips if the Email card is absent for the selected product. fillRequiredTemplateFields() sets Basic Information name to Green Life Architect from the dataset and fills first template title/email. saveEmailQr() delegates to the shared logged-in finishing helper; reopenSavedEmailQr() opens by internal QR name.

The template dataset defines 10 templates maximum, 4,000 body characters, title samples of 255/1,000/5,000, valid/invalid email samples, 17 expected icon labels, example subject/body, persistence data, and five viewports. Those are test expectations in source, not independently verified product specifications. Management, validation, responsive and persistence specs exercise different subsets.

Sources: Email data, Email Page Object, Email helper, all creation specs.

Worked reference: save a Website QR

For a manual reference check with a suitable test account, open My QR Codes, choose Create, select Website, and enter example.com. Give the QR a name you can recognize and record that name. Click Next, complete the design step, then Create. Close the download window if it appears and find the same name in My QR Codes.

This is an illustrative sequence. For a particular test case, use its exact account setup, value and expected result. The optional code equivalent below creates a fresh account as part of its setup.

const user = await pageManager.registerPage.authorizeUser()
await page.goto('/qr-codes')
await pageManager.menuPage.goToCreateQrCode()
const qrName = await pageManager.qrCreationPage.websiteQrCreate('example.com')
await pageManager.qrCreationPage.clickStep2NextButton()
await pageManager.qrCreationPage.clickStep3CreateButton()
await pageManager.qrCreationPage.closeDownloadModalIfPresent()
await page.goto('/qr-codes')
await pageManager.myQrCodesPage.expectQrVisibleInList(qrName)
// The surrounding spec must retain user.email and clean it up in afterEach.

To check that content was saved, reopen the QR by name and compare the website value. To check scanning, use its QR link and visit the destination. These are additional checks; not every creation test performs them.
