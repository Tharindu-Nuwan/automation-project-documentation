APIs, database, mail, and cleanup

Start · Previous · Next: QA workflow

Optional technical detail. Some automated cases prepare or verify records behind the product screens. This page explains those operations for test maintainers. If a manual check needs a particular plan, email, or account state, ask for that prepared state; you do not need to run database commands yourself.

UI tests also manipulate backend state

apiManager contains userApi, stripeApi, and dbApi. UserApi talks to the selected application's test endpoints. StripeAPI talks to Stripe. DbApi connects directly to MySQL. Mailpit has its own HTTP context and is instantiated separately. These are different systems and can fail independently.

selected project baseURL → UserApi → application test endpoints
selected env DB fields → DbApi → selected product plan schema
STRIPE_* → StripeAPI → Stripe customers/subscriptions/invoices/clocks
MAILPIT_* → MailpitApi → captured outgoing messages

Source: APIManager, fixture, API client.

DbApi: where the configuration comes from

The active IDE file, api/DbApi.ts, is a MySQL helper. Its constructor accepts DbConfig: product plus host/user/password/planName/emailName. The custom fixture passes these from the selected product's env; it does not read a global DB name internally.

requireConnection('plan') requires DB_HOST, DB_USER, DB_PASSWORD, and the selected <PRODUCT>_DB_PLAN. The optional email target would require <PRODUCT>_DB_EMAIL. Missing values produce an error naming missing keys, without printing credentials. ApiManager can be constructed with only a product fallback, but that does not supply a usable DB connection.

Connections use MySQL port 3306, 30-second connect timeout, and up to three connection attempts. Each public query operation normally opens and ends a connection in finally; this is not a connection pool. Polling opens repeated connections. The class comment mentions email DB support, but current public methods all use the plan target. Declaring email DB names does not mean emails are read through SQL.

How QR table discovery works

DbApi queries INFORMATION_SCHEMA.COLUMNS in the configured plan schema. It searches for a UID column (uId, uid, unique_id, qr_uid) plus user_id, with optional datetime/last_datetime. Selection preference is qr_codes, then a QR-named non-view table, then the first candidate. The chosen shape is cached on the instance.

Orphaning requires a datetime column. It sets SQL dates using database NOW() - INTERVAL 1 MONTH; the poll verifies owner is NULL and date is at least 20 days old. This combines database time and JavaScript time. A schema with several plausible tables should be checked before relying on the automatic choice. These methods act on the exact UID supplied by the test; use a test-created QR.

For full implementation and source-line details: API method reference. These are code behavior descriptions, not claims about the actual deployed schema, grants, replication topology or current connectivity.

Stripe helper and pricing evidence

StripeAPI uses STRIPE_BASE_URL or https://api.stripe.com and an authorization header from STRIPE_SECRET_KEY. It reads prices/coupons, finds customers by email, inspects subscriptions/schedules/invoices/discounts, and provides mutation helpers for cancellation, payment methods, subscription creation/coupons and test clocks.

UI checkout is asynchronous. Customer/subscription lookup has wait helpers; retry tests wait for test-clock readiness and invoice/status updates. Do not replace these with a single immediate fetch and assume missing records are final. Exact timeouts/defaults are in Stripe source and retry helper.

Pricing checks have separate sources: expected files/CSV, actual Stripe API records, database plan/trial records, and visible UI text. A useful assertion compares independent sources with the right plan, currency and discount. Reading one source twice is not a cross-system consistency check. Do not label source snapshots as current pricing without a live comparison.

Mailpit matching details

The client requires MAILPIT_BASE_URL; if MAILPIT_USER is set it sends Basic auth with that user/password. It first searches /api/v1/search by recipient (limit 50), then falls back to the latest /api/v1/messages (limit 50). Matching checks recipient case-insensitively, optional subject substring case-insensitively, and timestamp with a two-minute tolerance. Unparseable timestamps bypass that time test. Thus a timestamp alone is not perfect isolation; unique recipients and relevant subject filters matter.

waitForEmail() defaults to 60s timeout and 5s polling, then fetches again to return a matching message. Other methods retrieve HTML, plain text, raw message, details, count messages or assert no message within a window. An absent email can mean trigger failure, asynchronous delay, wrong recipient/subject, or mismatched SMTP catcher. Source: Mailpit.
