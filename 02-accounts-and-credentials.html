Accounts, login, and credentials

Start · Previous: your first check · Next: QR creation

Get the right account before starting

For a manual check, start with the test website address and an account prepared for that test. An account on one product or test website may not exist on another. This guide explains where the suite gets its values; it does not contain working team passwords.

  1. Confirm the product and test website with the person maintaining the test environment. Here, environment means the particular website and its connected test data.
  2. For ordinary login, request the existing test account email and password used by the login case. The automation names these settings DEFAULT_USER_LOGIN and DEFAULT_USER_PASSWORD.
  3. Confirm the required account condition: new, free, trial, paid, expired, or containing existing QR codes. An account with the wrong condition can show different pages.
  4. For registration checks, use a new test identity agreed for that environment. A generated email is only a value until the registration form has actually been submitted successfully.
  5. Record which test account you used in your private test notes. Share results without its password or login codes.

If you only perform manual checks, you do not need to create a configuration file or run the code shown later. The automation maintainer can supply the appropriate account and any prepared records.

Sign in through the browser

  1. Open the assigned test website's login page.
  2. Enter the existing account email and submit it.
  3. When the password field appears, enter that account's password and submit again.
  4. Check the destination required by the case. Submitting the form alone is not evidence that login succeeded.

If the account uses an email code instead, follow the code flow and use the message for that same email address and request. If neither the expected password field nor the expected code flow appears, record the page and account type before asking the maintainer to check the account.

Optional automation detail follows. A helper is a reusable piece of automation. A spec is a file containing test cases. Names such as authorizeUser() describe what the automation calls; you do not type those names into a form.

Generated registration, line by line

createUserData(false) builds rightmo-auto-<9–14 alphanumeric characters>@test.com. Its generated password equals that generated email. With true, the suffix is @mailtrap.com. These are disposable test identities, not credentials to request from an administrator. The random generator is not centrally seeded in BasePage.

authorizeUser() obtains that object, navigates to /register, calls signUp(email, password), and waits up to 25 seconds for Step 1's QR-type heading. It returns the object to the caller. A later setup failure can occur after registration but before the returned object is assigned, so a hook that assumes userData always exists can fail cleanup too.

The signup spec also tests duplicate registration using DEFAULT_USER_LOGIN / DEFAULT_USER_PASSWORD; generated data alone cannot reproduce the already-registered-email case. These values must belong to an account on the same target deployment.

Existing login is a two-step UI

  1. Open /login.
  2. logIn(email, password) waits for email input, fills it, then clicks the login button.
  3. The application resolves the email (the Page Object comment identifies /api/guest_data).
  4. The helper waits up to 15 seconds for the password input to become visible.
  5. It fills password and clicks the login button again.
  6. The test must verify the destination. logIn() itself does not assert a dashboard URL; expectLoggedIn() is a separate helper.

If the password field never appears, inspect the account lookup response and target deployment. A wrong or passwordless identity can follow a different UI branch; increasing the timeout will not fix the account. Source: LoginPage.

completeOtpVerification() types the code into the first OTP field with 100 ms delay, then verifies. expectResetLinkRejected() expects navigation away from reset-password and a hidden new-password field; it does not expect an invented “expired link” toast. The password-changed suite exercises positive and negative email behavior, reset reuse/rejection and browser-specific cases; its exact setup and assertions are in email reference.

Mail arrival alone does not prove password change or successful authentication. Keep the UI submission, message assertions, and fresh login evidence separate.

Configuration ownership and acquisition

The code tells us the variable names, but cannot establish who currently owns access or whether an account/key still works. Before using a test environment, get its website URLs and approved access from the person maintaining that deployment/CI. Confirm the identity exists there and has the expected account state. Do not copy another product's DB/schema or Stripe credentials by assumption.

Credentials, shared accounts and cleanup

Store local credentials in the ignored .env, with values obtained through the team's approved channel. Quote values containing dotenv-special characters such as #. Do not commit the populated file or copy its contents into shared reports. The guide documents sources rather than copying live credentials.

There is a concrete logging caveat: UserApi.loginWithPassword() currently prints request data and raw/parsed responses. Those can contain passwords or tokens. Review and redact an actual run log before sharing it; this documentation task does not modify that code.

Most isolated specs use afterEach → userApi.deleteUser([user.email]). After account-email changes, verify cleanup uses the resulting identity, not only the original email. Some flows use existing accounts or keep seed data intentionally. The fixture does not provide a universal cleanup safety net. See API and cleanup chapter.
