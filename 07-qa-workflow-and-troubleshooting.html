A simple workflow for manual checks

  1. Choose one case. Write down the action and its expected result. Start with a defined login or Website QR case before combining several flows.
  2. Confirm the starting conditions. Record the product, test website, account condition, language, screen size or device, and starting page.
  3. Collect the inputs. Use account access and the input guide. Request the exact upload files and any specially prepared account or records.
  4. Perform the actions in order. Record what you entered and which QR or folder you created. For validation cases, keep the exact invalid or boundary value specified.
  5. Compare expected and actual results. Check the stage named by the case: preview, saved content, download, scan destination or email. Stopping on an earlier page is a different result.
  6. Record the outcome. Include screenshots and the relevant QR/folder name. If you could not start because access, a file or prepared data was missing, record that reason separately from an application failure.
  7. Finish the agreed cleanup. Remove only disposable records assigned to this case. Keep shared login and prepared analytics accounts. Confirm with the account owner if cleanup ownership is unclear.

Source-code sections are optional for manual testing. An automation maintainer can use them to explain a setup dependency, locate the exact input value, or investigate a failing automated step.

How to reproduce manually

Record the same product URL, language, screen size, account condition, and starting page as the failed run. Use its captured input values and exact upload file. If the report does not show those values, ask the automation maintainer to trace them using the input guide. Keep the same phone country, and reuse the recorded generated values instead of generating new ones.

Perform the same action and compare the same expected result. Some tests arrange an expired subscription, an older QR with no owner, or simulated payment dates before they start. Ask the maintainer for that prepared state; an ordinary free account will not reproduce it. If the automated steps work around a known product problem, include that in the reproduction notes.

Interpret result statuses correctly

Result / declarationMeaning
PassedThe assertions that actually ran succeeded
Passed after retry / flakyFirst attempt failed; inspect cause, do not describe as clean first-pass success
test.skip()Not executed under current conditions; often environment/product availability
test.fixme()Disabled known problem; no current successful execution evidence
test.fail()Executed with failure expected; unexpected pass means the expectation needs review
No tests foundPath/project/grep/ignore configuration or discovery issue; not a passing suite
Factory skipSelected product has no registered implementation for accessed page
Dataset row / test-case catalogue entrySpecification/data presence, not proof an executable case exists

Optional automation detail follows. The next sections help someone reading, running or changing the code. For a manual-only check, use the workflow above and the result-status table.

Optional automation detail: read a test in this order

  1. Imports: custom fixture or raw Playwright? Which data/helpers are used?
  2. Describe and metadata: ticket/TC, priority, Qase mapping, serial/parallel configuration.
  3. beforeEach / beforeAll: account source, route, plan state, seed records, mocks.
  4. Test body: data declarations → actions → assertions. A method may assert internally.
  5. afterEach / afterAll: user, QR, Stripe and artifact cleanup.
  6. Runtime gates: skip, fail, fixme, product proxy, missing environment and CLI filters.

Start with login, Website, then a folder helper. These expose the most common patterns before the larger billing/Event suites.

Optional automation detail: run a focused check

Set the required environment first. Commands are examples to run against an approved test deployment; they were not executed during this documentation audit.

# Inventory one feature without executing it.
QASE_MODE=off npx playwright test tests/logged-in-user/create-qr-code/website-qr.spec.ts --project=oqg-chromium --list

# One case, one worker, no retry masking.
QASE_MODE=off npx playwright test tests/logged-in-user/create-qr-code/website-qr.spec.ts --project=oqg-chromium --grep 'Fill only the required fields' --workers=1 --retries=0 --headed

# UI explorer for a narrow project.
QASE_MODE=off npx playwright test tests/logged-out-user/login --project=oqg-chromium --ui

# Capture a diagnostic trace explicitly.
QASE_MODE=off npx playwright test tests/logged-in-user/create-qr-code/website-qr.spec.ts --project=oqg-chromium --workers=1 --retries=0 --trace on

npx playwright show-report

# Landing visuals use a separate project name.
QASE_MODE=off npm run test:visual -- --project=oqg-chromium-visual --workers=1

Open a trace from its actual path in test-results/runs using npx playwright show-trace <path-to-trace.zip>. A trace exists only if capture was enabled. Do not expect first-retry video when retries were disabled.

npm run test:event caps workers at two but does not select one product or magically target the local Event stack. Append an appropriate --project=... and configure that project's URL. npm run test:billing uses one worker but likewise does not choose the product. Inspect --list for the selected command.

Optional automation detail: add or adjust a case

Use CLAUDE.md as the repository engineering standard. Current code includes legacy exceptions; copying one is not automatically the preferred pattern.

  • Put the spec in the feature folder and use feature-based *-automations.spec.ts naming for new work.
  • Import test from @/fixtures/baseFixture, expect from @playwright/test. The fixture does not export expect.
  • Use pageManager and apiManager; reuse base helpers, existing locators and feature helpers.
  • Keep new cross-directory imports on @/; preserve unrelated legacy imports.
  • Put new environment-backed product values in env.ts; consume the selected env fixture, pass only needed fields.
  • Put deterministic cases in tests/data/<feature>.data.ts; pass one-off overrides to helpers instead of changing shared defaults.
  • Use actual existing data-qa-id/role/label selectors; inspect the DOM before adding a selector.
  • Record ticket, covered TC comments/annotations, priority and Qase metadata. Repository convention uses qase.id(0) for new unmapped tests; preserve existing IDs.
  • Create isolated accounts when supported, retain their identity, and implement cleanup that can cope with setup failure.
  • Add assertions for the intended behavior; don't mistake navigation or a visible modal for end-to-end persistence.
  • Run focused checks appropriate to the changed files, then the smallest supported product/browser set. Do not expand to every project by default.

Use the multi-product playbook only when deliberately migrating a flow. Product differences in selectors belong in Page Objects; different product requirements deserve separate tests. Existing factory registrations do not justify pretending unsupported products are covered.

Evidence for a useful bug or automation report

Record commit, exact command/project, deployment, test/TC name, sanitized setup/data source, expected vs actual result, first failing action/assertion, and relevant screenshot/trace/API status. State whether retries occurred, a mock or workaround ran, and cleanup succeeded. Keep live credentials and tokens out of shared evidence; the current UserApi logger makes log review especially important.
