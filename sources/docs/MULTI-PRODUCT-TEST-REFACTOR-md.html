30 ## When to use a factory (and when not to)
31 
32 Decide this **before** converting a page. Do not default to abstract + `Oqg*` /
33 `Qci*` / `Qga*` subclasses.
34 
35 | Situation                                                                | Pattern                                                                                                                                                               | `PageManager`                                                              |
36 | ------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
37 | Locators **and** page behavior are the same across the products in scope | One concrete `FeaturePage` + one `FeaturePageLocators`. No abstract class, no empty product subclasses, no factory.                                                   | `this.featurePage = new FeaturePage(page)`                                 |
38 | Same public methods, **different** selectors or clicks per product       | Abstract shared contract + product Page Object/locator classes + the constructor-style `PageFactory({...})`. Register only products that actually implement the page. | `this.featurePage = new FeaturePage(page, product)` in the **constructor** |
39 | Requirement / expected result differs by product                         | Separate tests. Do not force one abstraction.                                                                                                                         | —                                                                          |
40 
41 **Same page means:** the same elements, the same selectors, and the same
42 interaction steps. Empty `OqgFeaturePage` / `QciFeaturePage` classes that only
43 call `super(page)` are a signal the factory is unnecessary — collapse them to
44 one concrete class.
45 
46 Examples:
47 
48 - **No factory:** `MyQrCodesPage` — shared listing/folder UI.
49 - **Factory:** `DpfCreatePage` / `DpfGeneratePage` — OQG and QCI locators differ.
50 
51 Do **not**:
52 
53 - Add `Oqg*` / `Qci*` / `Qga*` classes that contain no product-specific code.
54 - Point QCI/QGA at the OQG class as a fallback.
55 - Use lazy getters (`get featurePage()`). Construct the product page in the
56   `PageManager` constructor like every other page.
57 - Convert a shared concrete page to a factory “just in case” products might
58   diverge later.

62 ## Non-negotiables
63 
64 1. **Structure only.** Keep existing test logic, assertions, cleanup, waits, and
65    coverage unless the user asks to change behaviour.
66 2. **Do not invent requirements.** The official test-case sheet is the source.
67 3. **One complete flow.** Leave unrelated pages and legacy suites alone.
68 4. **Do not mix product-selection models** in the migrated flow. No
69    `getDomain()` / `isOqg()` / `isQci()` / `isQga()` once the flow uses the
70    `product` fixture.
71 5. **Implemented products only** when a factory _is_ required. No empty
72    placeholders or cross-product fallbacks. An unregistered product passes
73    through the shared factory without breaking `PageManager` construction.
74 6. **Specs stay product-agnostic.** Product DOM and clicks live in Page Objects.
75 7. **Product bugs stay product bugs.** `test.fail()` / `test.fixme()`, never
76    `test.skip()`.
77 8. **Never invent `data-qa-id`.** Confirm the live DOM first.
78 9. **Use the root alias in new code.** Use `@/` for imports that cross repository
79    directories and `./` for modules in the same directory. Do not rewrite unrelated
80    legacy imports only to adopt the alias.
81 10. **Use the central environment config.** Add environment-backed values to `env.ts`
82     and consume the selected product through the `env` fixture. Do not add new direct
83     `process.env` reads to migrated code.
84 
85 ### Imports and environment configuration
86 
87 New files created by a migration use the TypeScript `@/` alias for cross-directory
88 project imports:
89 
90 ```typescript
91 import { BasePage } from '@/base/BasePage'
92 import { test } from '@/fixtures/baseFixture'
93 ```
94 
95 Keep relative `./` imports for modules in the same directory. Existing files may retain
96 their relative imports; a migration must not create unrelated import churn.
97 
98 Keep `env.ts` as the simple `defineEnv()` configuration with its existing `shared`,
99 `oqg`, `qci`, and `qga` structure. Add a value with `get('EXACT_VARIABLE_NAME')` in
100 `shared` or the applicable product object. Do not add loaders, helper functions, custom
101 validation layers, or unrelated logic to `env.ts`.
102 
103 - Tests receive product-specific configuration through the `env` fixture.
104 - If a config file or helper must import `env.ts`, use the named import `env`:
105   `import { env } from '@/env'`.
106 - `get()` is optional by default. Add `{ required: true }` manually only when that one
107   value must exist whenever `env.ts` is imported. Never mark every variable as required;
108   doing so can stop unrelated products and tests during configuration startup.
109 - Pass only the environment field a Page Object or helper needs. Do not pass, log,
110   attach, or snapshot the complete environment object.

114 ## Workflow
115 
116 ```
117 - [ ] 1. Inventory the current suite
118 - [ ] 2. Read the official TC sheet
119 - [ ] 3. Decide factory vs one concrete page (table above)
120 - [ ] 4. Convert Page Object + locators; factory only if needed
121 - [ ] 5. Wire PageManager in the constructor
122 - [ ] 6. Extract kebab-case data + helper
123 - [ ] 7. Split specs by concern
124 - [ ] 8. Apply metadata, titles, tags, qase
125 - [ ] 9. Update playwright.config only if filenames/tags changed
126 - [ ] 10. Verify (lint + targeted product run)
127 ```
128 
129 ### 1. Inventory
130 
131 Read the current spec(s) and list:
132 
133 - Which Page Objects and helpers the tests actually call.
134 - Which products the TC sheet / user named (often **OQG only**).
135 - Whether locators/behavior already differ by product, or are shared.
136 - Existing `playwright.config.ts` `testMatch` / `grep` that mention the old
137   filename.
138 
139 Do **not** migrate supporting pages just because the test uses them.
140 
141 ### 2. Official test cases
142 
143 Use the sheet the user points at. Record covered / skipped / not-yet-covered
144 TCs. A bundled test takes the **highest** priority among the TCs it covers.
145 
146 ### 3. Page Objects
147 
148 **Shared (no factory)** — match `MyQrCodesPage`:
149 
150 ```typescript
151 export class FeaturePageLocators extends BaseLocators {
152     constructor(page: Page) {
153         super(page)
154         // selectors
155     }
156 }
157 
158 export class FeaturePage extends BasePage {
159     locator: FeaturePageLocators
160 
161     constructor(page: Page) {
162         super(page)
163         this.locator = new FeaturePageLocators(page)
164     }
165 }
166 ```
167 
168 **Different pages, selectors, or interactions per product (factory)** — match
169 `DpfCreatePage` / `DpfGeneratePage`. `PageFactory({...})` is the standard factory
170 API: it receives the implemented product constructors and returns the class that
171 `PageManager` instantiates.
172 
173 ```typescript
174 import type { Page } from '@playwright/test'
175 import { BasePage } from '@/base/BasePage'
176 import { PageFactory } from '@/base/PageFactory'
177 
178 abstract class SharedFeaturePage extends BasePage {
179     protected abstract readonly locators: FeaturePageLocators
180 
181     abstract completeFeatureFlow(): Promise<void>
182 }
183 
184 class OqgFeaturePage extends SharedFeaturePage {
185     protected readonly locators: OqgFeaturePageLocators
186 
187     constructor(page: Page) {
188         super(page)
189         this.locators = new OqgFeaturePageLocators(page)
190     }
191 
192     async completeFeatureFlow() {
193         // OQG selectors and interactions
194     }
195 }
196 
197 class QciFeaturePage extends SharedFeaturePage {
198     protected readonly locators: QciFeaturePageLocators
199 
200     constructor(page: Page) {
201         super(page)
202         this.locators = new QciFeaturePageLocators(page)
203     }
204 
205     async completeFeatureFlow() {
206         // QCI selectors and interactions
207     }
208 }
209 
210 export class FeaturePage extends PageFactory({
211     oqg: OqgFeaturePage,
212     qci: QciFeaturePage,
213     // Add qga only when its page and selectors are implemented.
214 }) {}
215 ```
216 
217 `PageFactory` infers the shared public surface from the constructor registry, so
218 do not pass a generic or repeat a `Record` return type. Register constructors,
219 not page instances or callbacks. Keep concrete product classes private to the
220 module; when the shared contract has no external consumer, keep it private too.
221 Export only the generated feature class used by `PageManager`.
222 
223 If the selected product is not registered, constructing `PageManager` still
224 succeeds. Accessing that feature page skips the test with a clear unsupported-
225 product reason. Never map an unsupported product to another product's page as a
226 fallback, and only run a spec on products where that page is implemented.
227 
228 Never extend `Oqg*Page` from `Qci*Page` or the reverse. Specs always use
229 `pageManager.featurePage`, never `new OqgFeaturePage(page)`.
230 
231 ### 4. PageManager
232 
233 Always construct in the constructor. Both factory-backed and shared pages use
234 their exported concrete class directly.
235 
236 ```typescript
237 this.dpfCreatePage = new DpfCreatePage(page, product)
238 this.myQrCodesPage = new MyQrCodesPage(page)
239 ```
240 
241 Default `product: 'oqg'` on `PageManager` so the legacy `chromium` project still
242 works.
243 
244 ### 5. Data and helpers
245 
246 | File                                       | Name                        | Lives in         |
247 | ------------------------------------------ | --------------------------- | ---------------- |
248 | Constants, viewports, payloads             | `{kebab-feature}.data.ts`   | `tests/data/`    |
249 | Setup / shared flows used by several specs | `{kebab-feature}.helper.ts` | `tests/helpers/` |
250 
251 Extract what the old spec already had. Fake data still comes from `BasePage`.
252 Helpers take `pageManager` and must not instantiate Page Objects.
253 
254 ### 6. Split specs by concern
255 
256 Filenames: `{short-kebab-feature}-{concern}-automations.spec.ts`.
257 Create a file **only when there are tests for that concern**.
258 
259 Keep the feature folder (`tests/logged-in-user/my-qr-codes/`, not `tests/v2.5.0/`).
260 Delete the old monolith spec once the split files contain the same tests.
261 
262 ### 7. Spec file shape
263 
264 Match 2434 / 1424 / 2219: file header, covered-TC comment, `test` from
265 `@/fixtures/baseFixture`, `expect` from `@playwright/test`, title const shared with
266 `qase.title()`, format `{Jira}-{TCid}: {sentence}`.
267 
268 Every test records its sheet IDs in **both** a comment and Playwright
269 `annotation` metadata (`type: 'testId'`). Suite comment lists every ID in the
270 file; each test has `@covers` plus `annotation: [{ type: 'testId', description: 'OQG3-XXXX-TC##' }]`.
271 A test that covers several TCs lists every ID. Do not leave coverage implied
272 by the title alone.
273 
274 Logged-in suites always clean up created users in `afterEach`.
275 
276 ### 8. Config
277 
278 Only touch `playwright.config.ts` when the migration changes something it
279 already named. Do not expand CI to every product/browser as part of one feature.
280 
281 Run with `--project=oqg-chromium --retries=0`. Add other products only when
282 those Page Objects exist **and** the same test case applies.

286 ## What not to change (unless asked)
287 
288 - Unrelated specs, even in the same folder
289 - Supporting Page Objects the flow only _uses_
290 - Existing locator strings that already work
291 - Extra asserts, toasts, or waits “to be safer”
292 - Rewriting a working test body to look nicer
