35 ## 2. Environments — know which one you are targeting
36 
37 There is **no single "the environment"**. Three exist, and a suite that passes on one
38 may be impossible to run on another.
39 
40 | Environment     | URL                                        | What runs there                                |
41 | --------------- | ------------------------------------------ | ---------------------------------------------- |
42 | **dev**         | `https://oqg.dev.test-qr.com/en` (default) | Everything except Event QR and the email suite |
43 | **staging**     | `https://oqg.staging.test-qr.com/en`       | Historical target; same coverage as dev        |
44 | **local Event** | `http://192.168.1.185:8000`                | **Event QR only** (guest `/create` funnel)     |
45 
46 `baseURL` defaults to **dev** (`playwright.config.ts`). Override per run — the shell
47 variable wins over `.env`:
48 
49 ```bash
50 BASE_URL='http://192.168.1.185:8000/en/' npx playwright test tests/logged-in-user/create-qr-code/event-qr
51 ```
52 
53 **Why Event QR is local-only:** Event isn't deployed to dev/staging, and the local stack
54 has `/register` disabled (302 → home), so `authorizeUser()` — which _registers_ a fresh
55 user — cannot run there. Event is therefore exercised through the **guest `/create`
56 funnel**. Note `/login` **does** return 200 on local, so a login-based flow is possible
57 if a persistent local account exists.
58 
59 `playwright.config.ts` `testIgnore` excludes `**/emails/**`, `**/create-qr-code/event-qr/**`,
60 `**/event-qr-edit.spec.ts` and `**/visual/event-qr-percy.spec.ts` from dev-suite runs.
61 
62 **Timeouts are deliberately generous** (test 200s, expect 25s, action/navigation 90s)
63 because dev and local are slow, shared boxes. Low ceilings produced false
64 "element not found" failures. Don't tighten them to "optimise" a run. **[convention]**

66 ### Products and the migration path **[convention]**
67 
68 Product and environment are separate concerns:
69 
70 - **Product:** OQG, QCI, or QGA.
71 - **Environment:** local, dev, staging, or another deployed target.
72 - **Browser:** Chromium, Firefox, Chromium with Edge device settings, or WebKit.
73 
74 This repository is being migrated incrementally. Both execution models are valid while
75 that work continues:
76 
77 | Code                                            | Product selection                                            | Playwright projects                    |
78 | ----------------------------------------------- | ------------------------------------------------------------ | -------------------------------------- |
79 | Legacy, not yet migrated                        | `DOMAIN` / `BASE_URL` and helpers such as `getDomain()`      | Existing projects such as `chromium`   |
80 | New or deliberately migrated multi-product code | The typed `product` fixture and a product-specific `baseURL` | `oqg-*`, `qci-*`, and `qga-*` projects |
81 
82 Do not break, rewrite, or automatically migrate legacy tests just because the new model
83 exists. The existing projects and environment-based domain selection must keep working.
84 Migrate one complete feature or test flow at a time when requested.
85 
86 A migrated flow must use one product-selection path from start to finish:
87 
88 ```text
89 Playwright project -> product fixture -> PageManager -> product Page Object -> product locators
90 ```
91 
92 Do not mix this with `getDomain()` or `isOqg()` / `isQci()` / `isQga()` inside the same
93 migrated flow. Mixing the two can open one product through the project while an older
94 locator silently selects another product from `DOMAIN` or `BASE_URL`.
95 
96 Current product projects are `<product>-chromium`, `<product>-firefox`,
97 `<product>-edge`, and `<product>-safari`, where `<product>` is `oqg`, `qci`, or `qga`.
98 The Edge-named projects use Playwright's bundled Chromium with Edge device settings; they
99 do not launch branded Microsoft Edge. The Safari-named projects use Playwright WebKit,
100 not the installed Safari application.
101 
102 New machines need the project dependencies and Playwright browser binaries:
103 
104 ```bash
105 npm install
106 npx playwright install chromium firefox webkit
107 ```
108 
109 Product projects read their targets from `OQG_BASE_URL`, `QCI_BASE_URL`, and
110 `QGA_BASE_URL`.
111 
112 ### Product-specific environment data **[convention]**
113 
114 `env.ts` is the single, simple configuration object for environment-backed values in the
115 multi-product model. Keep its existing structure unchanged: load `.env`, call
116 `defineEnv()`, and declare only the `shared`, `oqg`, `qci`, and `qga` configuration
117 objects. Do not add loaders, exported helper functions, custom validation layers, or
118 unrelated logic to this file.
119 
120 ```typescript
121 export const env = defineEnv((get) => ({
122     shared: {
123         adminAuthEmail: get('STAGE_ADMIN_EMAIL'),
124         adminAuthPassword: get('STAGE_ADMIN_PASSWORD'),
125     },
126     oqg: {
127         product: 'oqg' as const,
128         baseURL: get('OQG_BASE_URL', { required: true }),
129     },
130     qci: {
131         product: 'qci' as const,
132         baseURL: get('QCI_BASE_URL', { required: true }),
133         adminAuthEmail: get('QCI_ADMIN_EMAIL') ?? get('STAGE_ADMIN_EMAIL'),
134         adminAuthPassword:
135             get('QCI_ADMIN_PASSWORD') ?? get('STAGE_ADMIN_PASSWORD'),
136     },
137     qga: {
138         product: 'qga' as const,
139         baseURL: get('QGA_BASE_URL', { required: true }),
140     },
141 }))
142 ```
143 
144 `defineEnv()` merges `shared` values into each product and preserves the inferred type.
145 Put a value in `shared` only when it is a genuine default for every product. Put a
146 product-specific value or override directly in that product's object.
147 
148 Data flows in one direction:
149 
150 ```text
151 .env locally / CI secret store
152   -> env.ts/defineEnv()
153   -> project selects product + baseURL
154   -> baseFixture resolves env[product]
155   -> test receives the env fixture and passes only the needed fields onward
156 ```
157 
158 Only public execution data belongs in project `use`:
159 
160 ```typescript
161 use: { product: env.oqg.product, baseURL: env.oqg.baseURL }
162 ```
163 
164 Rules:
165 
166 - Add an explicit `get('EXACT_VARIABLE_NAME')` lookup to `shared` or the applicable
167   product object. Do not construct variable names dynamically or mutate `process.env`.
168 - Environment values needed by new or migrated product-aware code must be declared here;
169   do not introduce new direct `process.env` reads.
170 - Specs receive product-specific data through the `env` fixture. Page Objects must not
171   import `env.ts`; pass them only the field they need.
172 - If a config file or helper genuinely needs to import `env.ts`, always use the named
173   import `env`, for example `import { env } from '@/env'`. Do not alias it to another
174   name.
175 - `get()` is optional by default. Add `{ required: true }` manually only to an individual
176   variable that must exist whenever `env.ts` is imported. Never add `required` to every
177   variable: one missing value would make configuration startup fail and can break
178   unrelated products, helpers, and test runs.
179 - Shared tests may use only fields with a consistent shape across their supported
180   products.
181 - Keep `baseURL` in `use.baseURL` and navigate with relative URLs.
182 - Never put secrets in `metadata` or project `use`, spread the complete environment object
183   into `use`, or log/attach/snapshot secret values. Reports, traces, screenshots, videos,
184   and Qase uploads are potentially visible artefacts.
185 - Keep values in the gitignored `.env` locally and CI secret storage remotely; commit only
186   names/placeholders.
187 
188 `env.ts` is evaluated when it is imported, including while Playwright builds its project
189 list before CLI project filtering. This is why required validation must be deliberate and
190 limited to variables that truly are globally required at that point.
191 
192 The product projects currently have no product-specific `testMatch`. Playwright UI may
193 therefore display the repository's tests under every product project. Opening the UI does
194 not run a project, and selecting only `oqg-chromium` runs only OQG. However, an unfiltered
195 `npm test` or `npx playwright test` selects every configured project, including products
196 whose Page Objects may not be implemented. During this migration, select only the
197 implemented product projects for local runs and CI jobs. Do not report an all-project run
198 as supported while any selected product behavior remains unimplemented.

214 ## 3. Repository layout
215 
216 ```
217 api/        API clients & helpers (Mailpit, Stripe, User)
218 base/       BasePage, PageManager, APIManager
219 env.ts      Simple shared and product-specific environment configuration
220 tsconfig.json  TypeScript settings, including the `@/` repository-root path alias
221 fixtures/   baseFixture.ts — the only fixture file
222 pages/      BaseLocators and Page Objects — one folder per page/feature
223 tests/      Specs; tests/data/ holds test data; tests/helpers/ shared setup
224 utils/      Formatters, generators, and environment configuration support
225 scripts/    Node tooling (docs, generators) — not part of the test runtime
226 docs/       Generated guides & reports (md + html + pdf)
227 ```
228 
229 **Placement rules [convention]**
230 
231 - Specs live only in `tests/`; Page Objects only in `pages/`.
232 - Each Page Object gets its own folder: `pages/AccountPage/AccountPage.ts` +
233   `pages/AccountPage/AccountPageLocators.ts`.
234 - Never edit `playwright-report/` or `test-results/` — they are generated.
235 - Search for an existing locator before adding a new one; do not create duplicates.
236 - Register new Page Objects in `PageManager`, new API helpers in `ApiManager`.
237 - Never instantiate Page Objects or API helpers directly in a spec — go through
238   `pageManager` / `apiManager`.
239 - **Organize by product feature, not by release.** Paths describe the feature
240   (`tests/logged-in-user/billing-page/…`, `…/my-qr-codes/…`). Jira, release, and TC
241   ids are **metadata** (file header + Playwright tags) — see §8.
242 - Do **not** create nested release folders (`v2.7.0` inside `v2.6.0`) or a global
243   `tests/v2.5.0/` tree. Do **not** move/duplicate existing specs into release folders
244   when a requirement changes — update metadata/tags in place.
245 - Legacy `…/v2.5.0/` trees may remain; **new** work goes under the feature path.
246   Migrate a file only when you are already editing it.

276 ## 5. Selector strategy **[convention]**
277 
278 Use in this order; don't skip a level without a reason.
279 
280 1. `page.getByTestId()` — **preferred** (`data-qa-id`)
281 2. `page.getByRole()` — buttons, inputs, links, checkboxes
282 3. `page.getByLabel()` — labelled form fields
283 4. `page.getByPlaceholder()`
284 5. `page.locator('#id')` — stable ids
285 6. `page.locator("//xpath[@id]")` — XPath anchored on an id
286 7. `page.locator('.css-class')` — only if stable and unique
287 8. `page.locator('tag.class')` — last resort, document why
288 
289 ```typescript
290 // ✅ role-based
291 page.getByRole('button', { name: 'Website' })
292 // ✅ stable id
293 page.locator("//input[@id='input-email']")
294 // ✅ attribute selector
295 page.locator("a[href*='analytics']")
296 
297 // ❌ fragile positional XPath — flag for refactor, never replicate
298 page.locator("(//div[@class='feedback-radio-btn-wrap']/input)[2]")
299 ```
300 
301 **Never:** positional selectors like `(//div)[3]`, `nth(0)` without a `.first()`/`.last()`
302 rationale, `getByText()` for interactive elements, or CSS chains deeper than 3 levels.
303 
304 > **Never invent a `data-qa-id`.** Confirm it exists in the live DOM first. Three
305 > non-existent test-ids were shipped this way and cost hours of debugging. If the
306 > element has no test-id, either ask the FE team to add one or use the next
307 > selector tier — do not guess a plausible-looking name. **[convention]**

311 ## 6. Page Object Model
312 
313 The standard shape is two classes per page: locators, and behaviour. A multi-product
314 page may use a shared abstract behaviour/locator contract plus product-specific classes.
315 
316 ```typescript
317 // pages/ExamplePage/ExamplePageLocators.ts
318 import { Page, Locator } from '@playwright/test'
319 import { BaseLocators } from '../BaseLocators'
320 
321 export class ExamplePageLocators extends BaseLocators {
322     someButton: Locator
323     someInput: Locator
324 
325     constructor(page: Page) {
326         super(page)
327         this.someButton = page.getByRole('button', { name: 'Save' })
328         this.someInput = page.getByTestId('example-input')
329     }
330 }
331 ```
332 
333 ```typescript
334 // pages/ExamplePage/ExamplePage.ts
335 import { Page } from '@playwright/test'
336 import { BasePage } from '../../base/BasePage'
337 import { ExamplePageLocators } from './ExamplePageLocators'
338 
339 export class ExamplePage extends BasePage {
340     locator: ExamplePageLocators
341 
342     constructor(page: Page) {
343         super(page)
344         this.locator = new ExamplePageLocators(page)
345     }
346 
347     /** Fills the form and submits it. */
348     async fillAndSubmit(title: string): Promise<void> {
349         await this.locator.someInput.fill(title)
350         await this.locator.someButton.click()
351     }
352 }
353 ```
354 
355 **Rules [convention]**
356 
357 - Page Objects extend `BasePage`, never `BaseLocators`.
358 - Locator classes extend `BaseLocators` when they use its shared selectors. A locator
359   class with no applicable shared selectors may remain standalone.
360 - Locators are reached through the Page Object's locator object (`this.locator.x` or the
361   typed product equivalent), never declared as loose locator properties on the Page Object.
362 - `BasePage` provides `page`, `expect`, `openPage()` and the fake-data helpers.
363 - Add JSDoc to public methods.
364 
365 ### Reuse `BasePage` and `BaseLocators` first **[convention]**
366 
367 Before adding a locator, page helper, navigation wrapper, wait, assertion utility, or fake
368 data method, inspect `base/BasePage.ts` and `pages/BaseLocators.ts` and search their current
369 usage. Reuse an existing base member when its meaning and selector match the new flow.
370 
371 `BasePage` is the shared behavior foundation. It already provides:
372 
373 - the Playwright `page` and `expect` objects;
374 - `openPage()` with retry handling for transient network drops;
375 - `isInvisible()` and the documented `wait()` escape hatch; and
376 - the repository's fake-data helpers.
377 
378 Prefer those members over reimplementing equivalent behavior in each product Page Object.
379 For Page Object-controlled navigation, prefer `openPage()` when its retry behavior and
380 options fit the flow; use direct `page.goto()` only when the test needs different navigation
381 semantics.
382 
383 `BaseLocators` is the shared selector foundation. It contains common inputs, buttons,
384 navigation controls, QR creation elements, frames, alerts, and other selectors used by
385 multiple pages. Extend it and reuse matching inherited locators instead of redeclaring
386 them.
387 
388 Base reuse must remain meaningful:
389 
390 - Reuse an inherited locator only when it represents the same element and behavior on the
391   selected product.
392 - Add a new member to a base class only when it is genuinely shared across multiple pages
393   or product implementations. Keep feature- and product-specific members in their own
394   classes.
395 - Do not override a base locator with an unrelated element just to reuse a property name.
396 - Do not copy a base method or selector into OQG, QCI, and QGA classes. If it is truly common,
397   inherit it; if it differs, implement it separately in the product classes.
398 - Preserve existing base behavior during migration. Changing a shared base member can
399   affect many legacy suites, so inspect all usages and verify them before editing it.
400 
401 ### Product-specific Page Objects **[convention]**
402 
403 Use a factory **only when locators or clicks differ by product**. If they are the same,
404 use one concrete Page Object and locator class — no abstract class, no empty `Oqg*` /
405 `Qci*` / `Qga*` subclasses, no factory.
406 
407 | Locators and clicks           | Pattern                                                                                  | `PageManager` constructor                               |
408 | ----------------------------- | ---------------------------------------------------------------------------------------- | ------------------------------------------------------- |
409 | Same across products in scope | One concrete page + locator class (`MyQrCodesPage`)                                      | `this.myQrCodesPage = new MyQrCodesPage(page)`          |
410 | Different per product         | Abstract shared contract + product classes + constructor-style factory (`DpfCreatePage`) | `this.dpfCreatePage = new DpfCreatePage(page, product)` |
411 
412 Empty product subclasses that only call `super(page)` mean the factory is unnecessary —
413 collapse them. Do not add a factory “in case” products diverge later. Do not use lazy
414 getters; construct every page in the constructor.
415 
416 When products have the same requirement but **different DOM**, keep the test and public
417 page behavior shared and put selectors and UI interactions in product classes. Create
418 separate Page Object and locator classes only for the products that actually implement
419 that page and are in scope. Do not add empty placeholder classes, made-up selectors, or
420 boilerplate for products that are not implemented yet. Add the product class and factory
421 entry together when support is implemented later.
422 
423 Never extend one concrete product Page Object or locator class from another concrete
424 product class. OQG, QCI, and QGA classes may inherit only their shared abstract contract,
425 `BasePage`, `BaseLocators`, or a genuinely product-neutral helper.
426 
427 Use the constructor-style `PageFactory({...})` and register only implemented product
428 constructors. This is the default factory API for multi-product pages whose selectors or
429 interactions differ. The generated class is the feature page that `PageManager` constructs;
430 do not add a separate `Create*Factory` class or a `.get(product)` call. An unregistered
431 product does not break `PageManager` construction and is skipped with a clear reason when
432 the page is used; never return another product's implementation as a fallback:
433 
434 ```typescript
435 export class ExamplePage extends PageFactory({
436     oqg: OqgExamplePage,
437     qci: QciExamplePage,
438     // Add qga only when its Page Object and selectors are implemented.
439 }) {}
440 ```
441 
442 Keep the shared contract and product implementation classes module-private unless another
443 module genuinely consumes them. Export the generated feature class used by `PageManager`.
444 
445 - Share selectors only when they are genuinely identical.
446 - Keep different selectors in separate product locator classes; do not build one large
447   locator class full of product conditions.
448 - Do not create an empty product locator or Page Object class. Do not point an unsupported
449   product at another product's implementation as a fallback.
450 - Keep product-specific tabs, accordions, layout handling, and waits inside the product
451   Page Object rather than branching on the product in the spec.
452 - Prefer semantic public methods that describe the business action or assertion. Method
453   names are not prescribed: choose clear, verb-first names that match what the method does
454   and preserve an established local convention where it remains clear.
455 - Do not create an abstraction when the products have different requirements. Similar DOM
456   alone is not a reason to claim that two test cases are the same.
457 
458 ### Fake data — never use `faker` directly in specs **[convention]**
459 
460 Use the `BasePage` helpers: `fakeEmail()`, `fakeEmailWithMailtrapAccess()`,
461 `fakePassword()`, `fakeString(n)`, `fakeText(n)`, `fakeWord()`, `fakeCompany()`,
462 `fakeUrl()`, `fakeFirstName()`, `fakeLastName()`, `fakeUserName()`,
463 `fakePhoneNumber()`, `fakeCity()`, `fakeInt(min,max)`, `fakeNumber()`.
464 
465 Use `fakeEmailWithMailtrapAccess()` **only** for tests that read mail (now via Mailpit);
466 `fakeEmail()` everywhere else.
467 
468 Never generate realistic PII (real names, real emails, real phone numbers).

472 ## 7. Fixtures and managers
473 
474 `fixtures/baseFixture.ts` is the only fixture file.
475 
476 ```typescript
477 import { expect } from '@playwright/test' // ← expect comes from Playwright
478 import { test } from '../../fixtures/baseFixture' // ← test comes from the fixture
479 ```
480 
481 > **[enforced]** Importing `expect` from `baseFixture` throws at runtime
482 > (`_baseFixture.expect is not a function`). ESLint blocks it.
483 
484 `pageManager` exposes the registered Page Objects — `accountPage`, `adminPage`,
485 `billingPage`, `emailBodyPage`, `loginPage`, `mainPage`, `menuPage`, `myQrCodesPage`,
486 `paymentPage`, `planAndPricesPage`, `qrAnalyticsPage`, `qrCreationPage`,
487 `registerPage`, `step1Page`, `step2Page`, `step3Page`.
488 `apiManager` exposes `userApi` and `stripeApi`. Access locators through `.locator`:
489 
490 ```typescript
491 await pageManager.myQrCodesPage.locator.sidebarAnalyticsButton.click() // ✅
492 await pageManager.myQrCodesPage.sidebarAnalyticsButton.click() // ❌
493 ```
494 
495 > Note: `pages/ScannedPage/` exists as a Page Object but is **not** registered in
496 > `PageManager`. Register it there before using it, rather than instantiating it
497 > directly in a spec.
498 
499 For product-aware code, `baseFixture` supplies `product` to `PageManager`. Pages whose
500 DOM differs by product are created with `new FeaturePage(page, product)` from the
501 constructor-style factory; pages whose locators and behavior are shared use their regular
502 single-argument constructor. Specs must continue to use
503 `pageManager`; never instantiate `Oqg*Page` or `Qci*Page` directly. The same rule applies
504 to `Qga*Page` classes.
505 
506 `baseFixture` also supplies the selected product's `env` object:
507 
508 ```typescript
509 env: async ({ product }, use) => {
510     await use(env[product])
511 },
512 ```
513 
514 Fixtures wrap a test: values created before `await use(value)` are provided to the test,
515 and code after it is teardown. Therefore, a spec requests project-specific data by
516 destructuring `env` from the fixture:
517 
518 ```typescript
519 test('example', async ({ env }) => {
520     // env is resolved from the current project's product fixture.
521 })
522 ```
523 
524 Import `test` from `fixtures/baseFixture.ts`; importing Playwright's unextended `test`
525 does not provide `product`, `env`, `pageManager`, or `apiManager`.

529 ## 8. Test structure
530 
531 ```typescript
532 import { expect } from '@playwright/test'
533 import { qase } from 'playwright-qase-reporter'
534 import { test } from '../../../fixtures/baseFixture'
535 
536 test.describe('Suite Name', () => {
537     let userData: { email: string; password: string }
538 
539     test.beforeEach(async ({ page, pageManager }) => {
540         userData = await pageManager.registerPage.authorizeUser()
541         await page.goto('/relative-path')
542     })
543 
544     test.afterEach(async ({ apiManager }) => {
545         await apiManager.userApi.deleteUser([userData.email]) // always clean up
546     })
547 
548     /**
549      * @covers OQG3-1424-TC03
550      */
551     test(
552         'short descriptive title',
553         {
554             tag: ['@Smoke', '@High'],
555             annotation: [{ type: 'testId', description: 'OQG3-1424-TC03' }],
556         },
557         async ({ pageManager }) => {
558             qase.id(0) // new tests use 0 — no unique ids (see §8 "Qase IDs")
559             qase.title('short descriptive title')
560             qase.suite('Suite Name')
561             // ...
562         }
563     )
564 })
565 ```
566 
567 **Rules [convention]**
568 
569 - Use the 3-argument `test(title, { tag, annotation }, fn)` form.
570 - Start every test body with `qase.id` / `qase.title` / `qase.suite`.
571 - **Covered test IDs (required):** each test records the sheet IDs it covers in a
572   JSDoc `@covers` comment **and** a Playwright `annotation` (`type: 'testId'`,
573   `description` = full ID such as `OQG3-1424-TC03`). A test that covers several
574   TCs lists every ID in both places. The suite comment above `describe` still
575   lists all IDs in the file. Do not leave coverage implied by the title alone.
576 - Clean up created users in `afterEach`.
577 - Use relative paths in `page.goto('/x')`.
578 - Tests must be atomic — never depend on another test having run.
579 - Tags in use: `@Smoke`, `@Automated_smoke`, and the priority tags `@High` / `@Medium` / `@Low`.
580 - **Priority tag (required):** tag every test with its test-case priority from the test-case
581   document — `@High`, `@Medium`, or `@Low`. When one spec/test covers multiple TCs of differing
582   priority, use the **highest** (`@High` > `@Medium` > `@Low`). A `describe` takes the highest
583   priority among its tests.
584 - **Filenames are feature-only:** `{short-kebab-feature}-automations.spec.ts`
585   (example: `files-counter-automations.spec.ts`). The Jira ticket lives on the **branch**
586   (`{OQG3-XXXX}-{short-feature}-automations`, e.g. `OQG3-1424-files-counter-automations`), not in
587   the filename. Do **not** rename when the ticket is updated for a later release — refresh
588   metadata/tags only.
589 - **File-level metadata** on ticket-scoped / release-touched specs. The header block
590   goes at the **very top of the file**:
591 
592 ```typescript
593 /**
594  * Release version: v2.5.0
595  * Jira: OQG3-1424
596  * Feature: Folder file counter
597  */
598 ```
599 
600 and the **covered-test-cases comment goes immediately above the `test.describe`**
601 (not at the top of the file), so a reader sees which TCs the suite addresses right
602 where the suite begins. **IDs are enough** — keep it clean and clear; note skipped /
603 not-yet-covered TCs too so coverage is honest at a glance:
604 
605 ```typescript
606 // Test cases covered by this spec: OQG3-1424-TC03, TC04, TC05, TC09, TC10, TC12,
607 //   TC14, TC15, TC16, TC18, TC23, TC31, TC46, TC47, TC50
608 // Skipped (env/feature gaps): TC07, TC08 ; Not yet covered: TC19, TC33
609 test.describe('OQG3-1424 folder file counter', { tag: ['@High'] }, () => {
610     // …
611 })
612 ```
613 
614 When later updated for another release, keep the path/name and extend the header
615 (e.g. `Updated for: v2.7.0 — …`) plus the covered-TCs comment.
616 
617 - **Multi-TC helpers** may list covered TC ids on `@param page`:
618 
619 ```typescript
620 /**
621  * @param page OQG3-1424-TC03 | OQG3-1424-TC04 | OQG3-1424-TC05
622  * @param pageManager
623  */
624 ```
625 
626 - Filter runs by priority: `npx playwright test --grep @High`.
627 - Update metadata whenever coverage changes.

629 ### Multi-product tests and safe migration **[convention]**
630 
631 Write one shared test across OQG, QCI, and QGA **only for the products where the test
632 case, requirement, expected behavior, and meaningful assertions are the same**. Different selectors or interaction
633 steps are implementation details and belong in product Page Objects:
634 
635 ```typescript
636 await pageManager.dpfCreatePage.open({ fx: value })
637 await pageManager.dpfCreatePage.expectFxValueInAllLocations(value)
638 ```
639 
640 Do not put product selector branches in a shared spec:
641 
642 ```typescript
643 // ❌ product-specific DOM knowledge belongs in product Page Objects
644 if (product === 'oqg') {
645     // OQG selectors
646 } else {
647     // QCI selectors
648 }
649 ```
650 
651 Use separate tests when a feature exists on only one product, the requirements or
652 expected results differ, or sharing would require many product conditions. Do not force
653 unrelated cases into one abstraction merely to reduce duplicated code.
654 
655 When asked to "update to the new structure", "use the new way", or migrate existing
656 tests to product projects, perform a behavior-preserving migration:
657 
658 1. Inspect and preserve existing requirements, assertions, metadata, coverage, cleanup,
659    and behavior; do not invent missing requirements.
660 2. Separate shared requirements from product-specific ones. Follow §6 for independent
661    product Page Objects, locators, factories, and unsupported-product behavior.
662 3. Migrate one complete flow through project → fixture → `PageManager` → product Page
663    Object. Use relative navigation and do not mix in legacy domain helpers.
664 4. Leave unrelated legacy flows and projects unchanged.
665 5. Run every applicable product independently, then together; confirm failures identify
666    the correct product/browser project.
667 6. Keep differing behavior separate. Never weaken assertions or drop coverage to force
668    the new structure to fit.
669 
670 Example product runs:
671 
672 ```bash
673 npx playwright test <spec-or-feature> --project=oqg-chromium
674 npx playwright test <spec-or-feature> --project=qci-chromium
675 npx playwright test <spec-or-feature> --project=qga-chromium
676 npx playwright test <spec-or-feature> --project=oqg-chromium --project=qci-chromium
677 ```
678 
679 Include `--project=qga-chromium` only when the requested QGA behavior is implemented and
680 the same test case applies to QGA.
681 
682 Legacy tests continue to use their existing projects (for example, `chromium`) and their
683 existing `DOMAIN` / `BASE_URL` behavior until an intentional migration is requested.

718 ## 9. Waiting & timing **[enforced]**
719 
720 Hardcoded sleeps are the single biggest source of flakiness and wasted CI minutes.
721 
722 ```typescript
723 await page.waitForTimeout(3000) // ❌ ESLint error
724 ```
725 
726 ```typescript
727 await expect(element).toBeVisible({ timeout: 10_000 }) // ✅
728 await element.waitFor({ state: 'visible' }) // ✅
729 await element.waitFor({ state: 'hidden' }) // ✅
730 await page.waitForURL('**/dashboard**') // ✅
731 await page.waitForLoadState('networkidle') // ✅
732 ```
733 
734 **The one escape hatch:** `BasePage.wait(ms)` (`base/BasePage.ts`). Use it only when no
735 event-based wait exists, and add a comment saying why.
736 
737 **Legacy debt:** 32 files still contain hardcoded sleeps and carry a
738 `/* eslint-disable no-restricted-syntax -- legacy hardcoded waits (test debt) */`
739 header. That header is a marker, not permission: when you touch one of those files,
740 replace the sleeps you encounter and shrink the header's reach. Never add a new
741 disable header to get around this rule.
742 
743 Iframes:
744 
745 ```typescript
746 const frame = page
747     .getByTestId('phone-mockup-container')
748     .locator('iframe')
749     .first()
750 await frame
751     .contentFrame()
752     .locator('#LocationBlock')
753     .waitFor({ state: 'visible' })
754 ```

758 ## 10. Reliability & concurrency patterns
759 
760 Hard-won lessons — each of these caused a real failure.
761 
762 - **`await` every click.** An un-awaited dropdown click in `setQrCodeFont` raced the
763   option selection and produced an intermittent wrong-font failure.
764 - **Don't chain toggles.** Clicking an accordion twice in a row races the animation;
765   wait for the state between clicks:
766     ```typescript
767     await trigger.click()
768     await expect(trigger).toHaveAttribute('aria-expanded', 'false')
769     await trigger.click()
770     await expect(trigger).toHaveAttribute('aria-expanded', 'true')
771     ```
772 - **Don't assert on `input.files` after an upload.** The FE consumes the native file
773   input and clears it. Assert the resulting UI instead (preview image, Delete control):
774     ```typescript
775     await expect(page.getByTestId('...-image-delete-button')).toBeVisible()
776     await expect(page.locator('img[alt="Preview"]')).toHaveAttribute(
777         'src',
778         /^data:image/
779     )
780     ```
781 - **Expanded ≠ populated.** A section can be open (`aria-expanded="true"`) while its
782   content is gone. Assert the thing you actually care about.
783 - **Prove new tests under load** before calling them done:
784     ```bash
785     npx playwright test <file> --grep "<id>" --repeat-each=3 --workers=2 --retries=0
786     ```
787     `--retries=0` shows the true first-run result; retries hide flakes.

791 ## 10a. Security & attack-input testing **[convention]**
792 
793 Patterns used by the Event QR "heavy" suites (`event-qr-security-heavy`,
794 `event-qr-edge-cases`, `event-qr-resilience`) — reuse them, don't reinvent.
795 
796 - **Payloads live in data**, not inline: `tests/data/eventSecurityPayloads.data.ts`
797   (XSS, unsafe URL schemes, SQLi, template/command/CRLF injection, unicode/bidi,
798   DoS-scale strings, and `maliciousUpload()` in-memory files). Grow the set there.
799 - **Prove XSS didn't execute with a dialog spy** — a DOM-count check alone can race:
800     ```typescript
801     const dialogs: string[] = []
802     page.on('dialog', (d) => {
803         dialogs.push(d.message())
804         d.dismiss()
805     })
806     // ...feed payloads...
807     expect(dialogs).toHaveLength(0) // any alert() = a real, reportable XSS bug
808     ```
809     Then also sweep for inert markup in the page **and** the preview iframe (`frameView`).
810 - **Craft malicious uploads in memory** — no fixture files, and you control MIME:
811     ```typescript
812     await input.setInputFiles({
813         name: 'logo.png',
814         mimeType: 'image/png',
815         buffer: Buffer.from('<svg onload=alert(1)>'),
816     }) // MIME/extension mismatch
817     ```
818 - **Test error paths without a working backend** via `page.route`:
819     ```typescript
820     await page.route('**/api/steps/qr/content**', (r) =>
821         r.fulfill({ status: 500 })
822     )
823     // assert the UI does NOT advance and does not crash
824     ```
825     This is how the resilience suite covers 400/403/500/abort even when the local
826     save endpoint is down.
827 - **Fields with `maxlength` truncate input** — that is correct, secure behaviour.
828   Don't assert the full payload survives; assert it's stored (capped) and inert.
829 - A payload that **executes**, or an input that **500s/crashes** the app, is a real
830   **product bug** (§11) — document and quarantine, never weaken the assertion. Finding
831   these is the entire point of automating instead of manual-testing this QR type.

835 ## 11. When a test fails: triage & quarantine **[convention]**
836 
837 **The QA suite encodes expected behavior.** Investigate every failure before changing
838 the test; do not bend assertions to match a broken product.
839 
840 **Root cause first — classify every red before you change anything, and state which
841 class it is. Never guess:**
842 
843 | Class           | Action                                                                                                    |
844 | --------------- | --------------------------------------------------------------------------------------------------------- |
845 | **Test defect** | Fix the test / Page Object. Prefer fixing the existing test over rewriting a working one.                 |
846 | **Product bug** | **Keep the test**; mark it `test.fail()` or `test.fixme()` + document. A real find is a **good** outcome. |
847 | **Env gap**     | `test.skip()` with an env reason (missing key, service absent on this env, browser limit).                |
848 | **Data issue**  | Fix the data / fixture. Don't loosen an assertion to tolerate bad data.                                   |
849 
850 > Never weaken/delete an assertion, loosen a matcher, or raise a timeout merely to turn a
851 > test green. If the root cause is unclear, investigate or ask.
852 
853 ### Product bug → never `test.skip()`
854 
855 - **`test.fail()`** — the test **runs**, is expected to fail, and flips to _failing_ the
856   moment the product is fixed (so you're prompted to remove the marker). Use for
857   confirmed, deterministic bugs where running the test is cheap and safe. **Preferred.**
858 - **`test.fixme()`** — skipped, but explicitly flagged "known-broken, must be fixed". Use
859   when running the test is impossible or harmful (it hangs, blocks the run, or leaves bad
860   state), so a slow expected-failure isn't worth it.
861 
862 ```typescript
863 // Product bug UPL-1996-01: an HTML doc named photo.png (declared text/html) is
864 // accepted and served as text/html — expected: rejected. Reproduced on dev 2.6.0.
865 // See docs/Upload_Security_OQG3-1996_Bugs.md.
866 test(
867     'an HTML doc named .png is rejected, not served as HTML [AC2]',
868     { tag: ['@High', '@Security'] },
869     async ({ page, pageManager }) => {
870         test.fail() // expected to fail until UPL-1996-01 is fixed; flips to failing when it is
871         // ...assert the CORRECT behaviour (rejected). Do NOT change it to match the bug...
872     }
873 )
874 ```
875 
876 Then add a row to the matching bug report (`docs/Event_QR_Product_Bugs_Report.md`,
877 `docs/Upload_Security_OQG3-1996_Bugs.md`) — the main table for product bugs, the
878 "Local-env only" table for environment limitations.
879 
880 Use `test.skip()` only for a documented non-product reason: an inapplicable feature or
881 environment, browser limitation, unavailable dependency, or temporarily broken test with
882 a follow-up. If a change would hide a bug, alter expected behavior, or reduce coverage,
883 stop and explain.

887 ## 12. Debugging method **[convention]**
888 
889 1. **Run the real test and read the real error.** Don't theorise from the code.
890 2. **Confirm against the live DOM** before changing a locator or assertion — dump the
891    element/attributes you're targeting and verify it exists.
892 3. **Then** fix, and re-run the specific test (`--grep`) to confirm.
893 
894 **Use UI mode — it is the fastest way to debug a red test:**
895 
896 ```bash
897 npm run test:dev -- --ui
898 # Event QR (needs the local stack), PowerShell:
899 $env:BASE_URL='http://192.168.1.185:8000/en/'; npx playwright test tests/logged-in-user/create-qr-code/event-qr --ui
900 ```
901 
902 It gives you the failing line, a time-travel DOM snapshot, locator picker, and watch-mode
903 re-runs. It is interactive, so use it locally—not in CI. Throwaway probe specs are
904 diagnostic scaffolding: name them `_probe.spec.ts` and delete them before committing.

908 ## 13. Definition of Done for a test **[convention]**
909 
910 - [ ] Passes on its target environment
911 - [ ] Passes under concurrency (`--repeat-each=3 --workers=2 --retries=0`)
912 - [ ] No hardcoded sleeps; no invented test-ids
913 - [ ] Locators follow the selector ladder and live in a Locators class
914 - [ ] Existing `BasePage` behavior and `BaseLocators` selectors were reused where their
915       meaning matches; shared base members were not duplicated in product classes
916 - [ ] A new or migrated page uses one concrete Page Object when locators/behavior are
917       shared, or independent product classes + `PageFactory({...})` when they differ; unsupported
918       products fail clearly without placeholder classes or another product's implementation
919 - [ ] `qase.id/title/suite` present; created data cleaned up in `afterEach`
920 - [ ] Priority tag present (`@High`/`@Medium`/`@Low`); when a test covers multiple TCs of differing priority, the **highest** is used
921 - [ ] Any `skip`/`fixme`/`fail` carries a documented reason (§11) — a **product bug uses `fixme`/`fail`, never `skip`** — plus a bug-report row
922 - [ ] Happy path **and** at least one negative/error case covered
923 - [ ] For a migrated multi-product flow, the product is selected consistently through
924       project → fixture → `PageManager` → product Page Object; no legacy domain detection is
925       mixed into that flow
926 - [ ] A shared multi-product test represents the same test case and expected behavior on
927       every included product; product differences remain inside Page Objects and locator classes
928 - [ ] Each applicable product passes independently and shared cases run against all
929       applicable product projects without changing `.env` between runs
930 - [ ] Unrelated legacy tests and projects retain their existing behavior

974 ## 16. Secrets & data safety **[convention]**
975 
976 - Credentials, keys and URLs live in `.env` (gitignored) or the CI secret store. In
977   migrated product-aware tests they are resolved centrally by `env.ts` and exposed
