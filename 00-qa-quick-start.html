Your first check

Use this page when you have a test case to carry out and need to know where to begin.

A test case describes a starting situation, actions to take, and an expected result. A flow is a sequence such as logging in, creating a QR, or changing account details. Manual testing means you perform those actions in the browser; automation means a program performs selected actions and checks.

1. Get the starting details

You needWhat to confirmWhere to get it
Product and website addressThe exact URL, intended environment, browser, and language. The suite uses the product names OQG, QCI, QGA, and QGC; support differs by flow.Your assigned test case and QA lead or test maintainer.
Account or guest stateWhether to stay logged out, sign in, or register. For an existing account, confirm its plan and any required history.The approved test account shared through your team’s access process; see Accounts and login.
Input valuesWhich fields to fill, which to leave empty, and whether a value must be exact or can be a fresh example.The assigned case and What to enter and upload.
FilesThe exact file, type, and size where the case specifies them.Upload file inventory; obtain the real file from the repository or the test maintainer.
Expected resultThe visible result and stopping point. A validation message, preview, saved QR, and scan page are different results.The assigned case and the relevant QR type or other flow.
Records to keep or removeWhether this account or record is shared and whether later checks need it.The case owner or test maintainer. A manual browser session does not automatically perform the automated test’s cleanup.

If something is missing: record exactly what you need and ask the QA lead or test maintainer. For example: “I need an existing account on this test URL with a saved QR and scan history for the analytics check.” You do not need database access to request the correct starting state.

2. Choose the right account

For a login check, use the approved existing account. The usual automated login reads configuration entries named DEFAULT_USER_LOGIN and DEFAULT_USER_PASSWORD; these names are labels for stored settings, not values to type into the form. The actual password is intentionally absent from this guide.

For a registration check, use a fresh address following the case instructions and complete registration before attempting login. Automation can generate an email and password, but generating these strings alone does not create an account. If the case checks an email message, obtain access to the team’s test inbox as well.

Some flows require a special existing account. Analytics needs history; billing may need a particular subscription. A newly created empty account is not an equivalent replacement. Details and exceptions are in Accounts and login.

3. Choose values from the right source

4. Example: follow a Website QR through its stages

This example helps you understand the stages. If your assigned case specifies different values, actions, or expected results, follow that case. It is not a replacement for the full QR reference.

  1. Open the agreed test website in the required account state and begin creating a QR.
  2. Choose a type: select Website at the QR type step.
  3. Enter content: for an ordinary valid example, use a recognisable internal QR name such as QA-Website-check-01 and a URL such as https://example.com. Use a different name if needed to distinguish this run. The internal name helps you find the QR later; the URL is its destination.
  4. Check the form: compare the accepted values, validation messages, and preview with the expected result. If this is only a validation case, stop at the specified point.
  5. Continue if the case requires saving: proceed to the design step and complete the create/save action in the selected flow. A filled form or preview alone is not proof the QR was saved.
  6. Check the saved record: locate your QR by its name. If scanning is part of the case, scan the saved QR and compare the opened destination with the URL you entered.
  7. Record the result and remove only the test records that the case says to remove.

The suite has 18 top-level QR type choices. Menu has Digital, PDF, and Website variants, giving 20 paths when those are counted separately. Required fields differ by type; do not reuse the Website field list for Event, PDF, Email, or another type.

5. Record the result clearly

A useful result lets someone repeat your check. Capture the product and test URL, browser, account reference (without its password), starting state, exact input values or filenames, actions, expected result, actual result, time, and relevant screenshots. For a QR issue, include its name or identifier and whether the problem happened in the form, preview, saved record, or scan page.

If access or required data is missing, report that as a setup blocker. If the product behaves differently from the expected result, describe the difference. See Check results and report problems for a reporting template and automation result explanations.
